Three rings

The core governs. Plugins do the work.

Identity, permissions, runs, audit and budgets live in one small core. Everything a team works on — knowledge, tables, projects, mail — is a plugin, and yours use the same contract as the official ones.

Ring 1

Governance core

Accounts and roles, field-level policies, conversations and custom agents, tools and runs, the activity log, models with USD budgets and a gateway, the MCP server and outbound connectors, automations, Files, notifications and push, branding and the Admin place.

Ring 2

Official plugins

On by default: Knowledge, Tables, Skills, Feedback, Memory. Compiled in, off until you enable them: Projects, Reports, Email, Feishu, WeCom, Computer and Retro. Turning one off keeps its data.

Knowledge Tables Skills Feedback Memory Projects Reports Email Feishu WeCom Computer Retro

Ring 3

Your plugins

Your CRM, ERP bridge or domain data in plugins/<id>/. Describe an entity once and get governed agent tools, REST, search, export and client pages; add your own routes, jobs and an embedded UI when you need them.

Bring your own agent

Claude Code, Codex or Cursor — on your team's data.

Members add the station's address to their MCP client and sign in. Their agent gets the same tools Sprouty uses, narrowed to that member's permissions and the scopes they granted.

  • OAuth 2.1 with PKCE for people; machine clients bound to an internal member for jobs.
  • Writes run in the member's name and land in the activity log; deletes preview first and need a second, confirmed call.
  • Outbound connectors reach other MCP servers with team or personal credentials, read-only until you switch writes on.
  • An optional model gateway gives members OpenAI- and Anthropic-compatible keys that spend from the same budgets.

Trust boundary

Safe to point at your whole organization.

Only narrow, never widen

Every tool call is the intersection of the member's permissions, the client's scopes and the plugin's field policy.

Budgets before calls

Models, search, page reads, vision and images reserve USD from member, service and team budgets before the provider is called.

Real accounts only

No public sign-up, guests or anonymous agents. Every request binds to a current internal account.

Fail closed

The server refuses to start without a signing key; stored secrets need their own encryption key and are never shown again.

One client

Browser and iPhone, light and dark.

One universal client. The server hosts its web build at /; the native iPhone and iPad app adds widgets, notifications and offline copies, and switches between stations. Android and a macOS shell are in the repository as previews.

Plugins

Describe your data once. Get tools, REST and pages.

A plugin is a package: a pure-data manifest, an API half, its own migrations and an optional embedded UI. SDK 2 turns an entity definition into governed agent tools, REST routes, search, export and client pages.

// plugins/example/api/index.ts
export default defineExtension({
  ...manifest,            // id, sdk: 2, core range, pages, nav
  dataSources: [{
    app: defineApp({
      id: 'example',
      entities: { note: {
        table: 'ext_example_notes',
        accessScopes: ['own'],
        fields: {
          body: { kind: 'text', searchable: true },
          userId: { kind: 'user', title: 'Owner' },
        },
      } },
    }),
    entities: { note: {
      actions: { read: 'team', create: 'team' },
      audit: 'all',
      ownerField: 'userId',
    } },
  }],
  migrations: { dir: extensionPath(import.meta.url, '../migrations') },
  ui: { dir: extensionPath(import.meta.url, '../ui') },
});
  • Five page kinds: native, entity list, entity detail, settings form and embed.
  • Its own tables and migration lane; disabling a plugin keeps its rows.
  • An import-boundary scanner keeps plugins on the public kit, so private overlays merge cleanly.

Admin

Configure it from the browser.

Model and search keys, branding, team context, connectors and plugin status live in the Admin place and the database. Secrets are encrypted and write-only; branding applies at once, including the sign-in page.

Self-host

One image, one database.

The container serves the API and the web client. Add PostgreSQL and an API key for any OpenAI-compatible model; add an S3-compatible bucket when the platform has no disk.

Docker Compose
# secrets and your model endpoint
cp .env.example .env && ./scripts/gen-secrets.sh

# Postgres, migrations, API and web client
docker compose up -d --build

# the first super administrator
docker compose exec api pnpm admin:create
→ http://localhost:3000

Container platforms

Render, Fly.io, Railway, Zeabur, Sealos, Cloud Run and others: set MIGRATE_ON_START=1 and BOOTSTRAP_ADMIN_EMAIL, deploy, and open the activation link from the service log. A Render blueprint and a Fly.io config are included.
