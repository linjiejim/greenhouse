# 常驻 Agent：设计与取舍

更新 2026-10-14 · 状态：Jim 已确认（2026-10-14，另有补充，见 §7） · 配套 [PRD](prd.md)、[路线图](roadmap.md)、[功能清单](features.md)

依据：2026-10-14 的补充评审《从「能对话的 Agent」到「常驻的 AI 同事」》，它参考了 Grok Bot / Always-On Agent 报告。评审引用的代码已在 `v2@6190d8d6` 上逐条核对，结论属实。本文记录哪些采纳、哪些改写、哪些推迟、哪些不做，以及理由；路线图按本文调整。

## 1. 目标

PRD 的第一条价值是「每个人都有 AI 同事：在后台做事，只在需要时找你」。v2 现在能对话、能后台运行、能定时，离「常驻」还差五件事：

- 能叫醒 Agent 的只有人的消息和电脑里的进程结束。
- 后台运行只能读网页和知识库：不能写，也不能用电脑。
- 写共享对象一律发卡片。表格和应用上线后，写工具成倍增加，卡片会多到被当成橡皮图章，安全反而是假的。
  - 反过来，浏览器里的点击和输入算「只读」：在外部网站上提交、付款、发布，都不经过任何人。
- 几处「持久」只建了表、没写代码：批准后的执行、崩溃时正在跑的步骤、定时触发，都可能丢失或重复。
- 没有提示缓存。常驻意味着更长的对话和更多后台运行，成本和首字延迟会先成为瓶颈。

做完之后：
- Agent 默认休眠，被消息、运行结果、文档里的 `@`、表格事件叫醒。
- 在后台把能做的做完，要人决定的留成少量、清楚的卡片。
- 崩溃或发布后，从中断的那一步继续。
- 没事时保持安静。

## 2. 保持不变

这些设计已经是对的，不因为常驻而改：

- 单引擎、单写者，`conversation_inbox` 合并排队，租约加清扫。
- `jobs` 是唯一的后台队列。只依赖 PostgreSQL。
- 数据流防护：后台运行读过私有数据后就不能再出网。密码库由服务端代填，值不进对话。
- 公开 Agent 用提问人的权限、记忆和电脑，工具默认关闭。
- 每个 Agent 与每个成员各一台电脑，不改成「一人一台电脑、每个 Agent 一块屏幕」。
- 内置工具全部发送，并保持稳定。只有连接器和技能按需发现。
- 不加「最大步数」「温度」这类参数。v2.0 不做向量检索。

## 4. 设计要点

### 4.1 审批分级（AO-11）

按「可逆性 × 范围」分三档。每个工具按调用参数判断属于哪一档（`callRisk`）。

| 档 | 范围 | 处理 |
| --- | --- | --- |
| 1. 自己的、可撤销 | Agent 的私有文件夹；只有成员自己看得到的文档和表格；成员私有 Agent、一次性提醒、生成的私有文件 | 直接执行，在对话里留回执，可以撤销（靠文档版本、记录回收站、记忆回执） |
| 2. 共享的、可回滚 | 分享出去的文档；共享表格里的记录 | 发卡片。卡片上可以选「以后这个文件夹 / 这张表都允许」，之后这个 Agent 在这个范围内直接执行，并留回执 |
| 3. 对外或不可逆 | 发邮件；连接器的写操作；彻底删除；在浏览器里提交、付款、发布 | 永远发卡片，不能预先授权 |

预先授权：
- 按 Agent、成员、范围（文件夹或表格）、动作四项记录。
- 在 Agent 资料的「能力」分页列出，可以撤销。
- 只有成员能在卡片上授予。Agent 不能自己申请范围之外的授权。

卡片：
- 回合或运行读过外部内容（taint）后，不再使用预先授权，第 2 档照样发卡片。这样，注入进来的指令只能写到人看过的地方。
- 同一步里的多条写入合成一张卡片，比如表格里批量修改记录。

在哪里批：
- 第 1 档不推送，只在对话里留回执。
- 第 2 档：App 与 Web 的卡片上批；手机通知上的「批准」「拒绝」要先解锁；手表上按住确认。「以后都允许」只出现在卡片上。
- 第 3 档：只在 App 或 Web 的来源对话里批。手机上批准前过 Face ID 或系统密码；窄屏 Web 用通行密钥，没有就重输密码；桌面 Web 不加。锁屏、通知和手表只能打开它。

浏览器和电脑：
- 在浏览器里点击提交类元素算第 3 档：提交按钮、会提交表单的动作、写着「发送」「支付」「删除」「发布」的按钮。
- 例外：密码库代填并且已经获准的登录表单，提交时不再另发卡片。
- 电脑里的 shell 不分档。后台运行用电脑的规则见 4.3。

审查模型，即评审提出的「第 2 档由快模型审查」，v2.0 不做。理由：
- 预先授权是人做的决定，范围明确，可以审计，也不需要额外的模型调用。
- 审查模型等于让模型批准写进同事看得到的地方。在团队产品里，这改变了信任模型，应该等有数据再决定。
- 满足以下任一条件时再评估：每个活跃成员每天的卡片数中位数超过 10；或者批准率超过 95%。

PRD 原则 5 也相应改写，见 PRD §3。

### 4.2 唤醒层（AO-07）

- 一个入口：`engine.deliver(conversationId, event)`。
  - 事件写进 inbox，类型为 `event`、`run_report` 或 `handback`。
  - 默认送到 Agent 的主人和这个 Agent 之间的 Agent 对话；主 Agent 送到主线。
- 路由：
  - 按去重键去重。
  - 同一个 Agent 在 2 分钟内收到的事件合成一个回合，提示里写「有 3 件事」。
  - 优先级：成员的消息高于卡片的决定结果，决定结果高于事件。
- 上限：
  - 事件带有来源链，同一条链最多 3 层。
  - 每个 Agent 每天被事件叫醒的次数有上限，默认 50。超过后事件照样记录，但不再叫醒 Agent，主人收到一条通知。
- 安全：
  - 事件内容是不可信输入，要用 fence 隔开，也不代表任何人的同意。
  - 被事件叫醒的回合，按后台运行的规则执行（见 4.3）。
- v2.0 接入的来源：
  1. 后台运行结束后的跟进。简报里可以勾选「完成后继续」，默认不勾，避免成本翻倍。
  2. 电脑里的后台进程结束（已经实现）。
  3. 主人在知识库的文档或评论里 `@` 自己的 Agent。规则和房间一样：只有主人点名才叫醒。
  4. 表格自动化里的「执行 Agent 步骤」（随 M2.2）。
  5. Agent 邮箱的来信（随 M1.8）。发件人在名单里才叫醒（默认是主人和工作区成员）；其余来信留存，主人可以放行这个发件人。
- 放到 v2.1 的来源：
  - 成员个人邮箱的新信：经内置连接器，用 `jobs` 轮询。
  - 每个 Agent 一个签名的 webhook。
- 以后 IM 渠道里 `@Agent` 是人发的消息，走普通的发送，不算事件。

### 4.3 后台运行（AO-09、AO-08、AO-17）

工具：后台运行新增可以使用的工具：
- `memory` 的 `recall`。
- `conversation_query`，只能查来源对话。
- `mcp_call` 的只读工具。
- `computer`。

连接器连续读取：
- 已批准的后台任务可在第一次 `mcp_call` 读取时，用可选 `read_ahead` 一次声明同一连接器、同一账号的后续精确参数。最多 16 次后续读取，当前与后续参数合计不超过 8192 字节。两张已知订单的对比应在首次读取时声明两张订单，而非读取第一张后才补充第二张。
- 计划里的每个工具必须经管理员确认只读，且不标为破坏性；内置连接器经过审核的只读工具同样可用。仅有外部服务器的只读声明不够。工具列表和操作说明显示哪些操作可用于计划；管理员在「设置 → 连接器」确认只读。
- 计划在私有数据或其他来源内容进入运行前固定，不能追加、替换或转交其他运行、账号；允许先查看本地连接器列表和操作说明，事件或网页内容不能借此获得授权。后续参数如果依赖刚读取的结果，Agent 应报告缺少的工作，并请成员以明确参数开启新任务。
- 读过私有数据后仍可查看本地连接器元数据、复用本次运行已保存的同参数结果。每次都重查当前访问权限和凭据，撤销权限后不能复用。计划与结果绑定当前连接身份：重连、凭据或工具权限更新后需新任务；OAuth 在当前调用内刷新可以完成该调用，但后续计划会保守失效。
- 任意新 MCP 参数、其他连接器、网页请求和写入仍受原有边界约束。以上是可预知的多次读取，不是任意自适应私有数据访问。

拒绝操作的记录：权限、读取计划或数据外发规则拒绝工具时，运行详情保留失败步骤、稳定原因代码和可执行的说明。可恢复工具失败不自动让整次运行失败；成员应同时查看产出和步骤，不能仅凭运行结束状态认定全部业务目标完成。

写入：写工具按 4.1 分档。
- 第 1 档直接执行。
- 第 2 档：有预先授权、并且没读过外部内容时直接执行；否则发卡片。
- 第 3 档发卡片。
- 发卡片后，运行停在「需要你」；批准后从记录的步骤接着做（AO-04）。
- 效果是：夜里干完活留下草稿，早上一键批准。

电脑：
- 简报里要声明会用电脑，以及要访问哪些域名。成员批准简报，就等于同意。
- 后台运行用电脑期间，电脑出网只放行这些域名。Docker 适配器在这期间不联网。
- 「读过私有数据后不能出网」的规则照旧。

无事静默：
- 定时加一个开关「没有发现时不通知」，默认关。Agent 提议监控、巡检类的定时时，可以把它打开。
- 后台运行的结果里带一个 `findings` 字段。开关打开、又没有发现时，不发通知；这次运行照样出现在「运行」和对话里。
- 失败总是通知。

工作日志：
- 后台运行结束时，往 Agent 的记忆里写 1–3 行，带日期：做了什么、产物是什么、还剩什么没做。
- 记忆索引里只放最近 7 天的日志标题；`recall` 可以按日期查。

### 4.4 可靠性（AO-01 到 AO-05）

| 条目 | 做法 | 验收 |
| --- | --- | --- |
| 批准后的执行 | `settle` 和一条 `request_decided` 任务在同一个事务里写入，任一进程的决定 worker 领取并执行。步骤从 pending 到 running 用 CAS 迁移，保证只执行一次 | db-commit 测试：settle 之后进程退出，另一个进程领取任务，恰好执行一次 |
| 结果未知的步骤 | 工具声明自己是否幂等（`idempotent`）。非幂等工具遇到上次停在 running 的同键步骤时，把它标为 `uncertain`，不执行，并告诉模型先检查状态再决定。运行详情里单独显示 | 单元测试覆盖冲突分支；重试时非幂等步骤不重放 |
| 定时触发 | 在领取定时的事务里直接建运行，提交后再启动。停机期间错过的多次触发合成一次，并写进文档 | db-commit 测试：提交后进程退出，运行仍然存在，并且会被执行 |
| 按步骤续跑 | 每个模型步骤结束时，把新增的回复片段和工具结果写进 `run_steps`（kind 为 `model`），每步最多 2 万字。后台运行重试时，从记录的步骤重建上下文。回合续跑（M3.6）的条件：中断不到 10 分钟、发起人还在对话里、最后一步已经完成；满足时接着写同一条回复 | db-commit 测试：工具步骤完成后杀掉进程，另一个进程接手，工具不重放；62 分钟的长任务探针加一个「中途重启」场景 |
| 实时推送的热路径 | 回合开始时解析一次受众并缓存。文字增量每 50–100 ms 合成一帧。超过上限的事件，跨进程只发 `conversation.resync`，客户端按 `after_seq` 补拉。重连时只补拉当前打开的对话 | db-commit 测试：两个 hub 实例下，大于 7 KB 的最终消息能送到另一个进程；单元测试：一个回合里查询受众的次数是常数 |

### 4.5 成本（AO-06、AO-13）

缓存断点：
- 引擎只在消息上做中性的缓存断点标记，由 Anthropic 适配器翻译成 `cacheControl`。
- 断点放在三处：system 末尾、稳定历史的最后一条、上一轮的最后一条。
- OpenAI、DeepSeek 这类服务自动做前缀缓存，只需要前缀保持稳定。
- 厂商特有的写法只放在适配器里。

前缀稳定：
- 工具描述固定不变。每轮会变的清单（可用的连接器、装备的技能、本轮能画的富块）移到收尾消息 `<turn_context>` 里。
- 同一个对话里，工具的集合与顺序只在 Agent 版本变化时才变。
- 摘要的触发阈值按上下文窗口的比例设定，按预算截断历史只作为最后的兜底。

可见：
- 「我的用量」和管理里的用量页显示缓存命中率。
- 开发环境里，同一个对话从第二轮起命中率仍为 0 时打一条警告。

长输出：
- 工具输出超过约 8 千字时，存成成员的私有文件（30 天后清理）。工具结果只返回文件、开头一段和总长度，模型可以按区间读取。
- 不做滚动遮罩。

### 4.6 部署（AO-14、AO-15、AO-19）

- 用环境变量 `GREENHOUSE_ROLE` 区分进程角色：`all`、`api` 或 `worker`，默认 `all`，一行安装不受影响。
  - worker 负责后台运行、定时、jobs、电脑进程监视、清扫和摘要。
  - api 负责 HTTP、WebSocket 和前台回合。
- 收到 SIGTERM 后，不再接新回合；进行中的回合最多等 60 秒，剩下的交给另一个进程续跑。
- 限流抽出存储接口：默认用内存；多副本时用 PostgreSQL 的一张小表。
- Compose 部署的电脑用 E2B，在 README 和 compose 注释里写明。不把 Docker socket 挂进 api。
- Redis 只在以下任一条件成立时，作为可选适配器加入：
  - 常驻多个副本，并且在合帧之后，NOTIFY 或 PostgreSQL 的 CPU 仍然是瓶颈；
  - 前台回合迁到 worker；
  - 需要按 token 断线续播；
  - 公网接口需要跨副本限流。

### 4.7 内环（AO-16）

- `pnpm cli eval export <run | message>`：导出提示的各层、工具定义的哈希和各个步骤，存成测试夹具。
- `pnpm eval`：用脚本模型回放这些夹具，抓提示组装、工具开放和审批流程的回归。
- 素材来源：带评语的 👎、失败的运行、被拒的卡片、中断的回合、`uncertain` 的步骤。每周过一遍。
- 另外维护一小组真实模型用例，每晚运行（M3.6）。

### 真实模型验收补充（#70）

审批卡的显示文字与执行参数分开：结构计划和应用动作展示人类可读的对象、字段和值；知识正文显示安全 Markdown 短预览。步骤在批准前写「等你批准」，拒绝后写「未执行」，结果未知时不宣称未发生。同一回合同一数据表的可逆写入合为一张具名回执，撤销在一个事务中倒序处理全部步骤；批内连续修订可恢复，但成员在批外做过的修改仍冲突。

### 审批自动收敛决策（#70，U3）

通知只有一个列表，审批在来源对话的卡片中进行，并在对应对话的侧栏显示待处理提示、按设置推送。请求一旦批准、拒绝、回答、交还、过期、撤回或被取代，通知立即从所有打开的客户端、未读数与应用角标中清理；历史保留在对话。

新计划的同目标请求沿用统一 supersede 路径：范围限定同成员、对话、Agent 与主题，目标取执行参数，不取标题、翻译或新写入内容。问题按字段键，知识按文档／文件夹，表格按数据表／记录／结构所属 base，应用按动作，邮件按回复对象／草稿，其他按工具和明确目标；未知目标不替换。已完成的模型步骤可以用新请求取代旧卡，同一步骤内批量写仍是一张卡。

成员直接在对话中打字会将该回答 Agent 的待处理问题标为 superseded，原因为 answered in chat；原消息就是答案，审批卡不受影响。取消 run 或 turn 将它未处理的请求标为 withdrawn，等待步骤跳过，不再外发通知。第 2 档同范围、同动作的批准可同时结清该对话其他适用请求；污染状态、原权限与版本检查仍有效，每项写入独立生成回执。第 3 档永远逐卡人批。
