## 分支与节奏

- PR #64（表格 → 应用）由 Jim 合并；v2 的表格与应用（M2）从它的实现移植。
- 合并后给 v1 打最终标签，从它拉出 `release/v1`，只收安全和严重缺陷修复。现有部署（green.linjiejim.com、私有 overlay）留在 v1，直到它们决定迁移。
- v2 在长期分支 `v2` 上进行，草稿 PR #70 跟踪进度。每个切片是一组提交，完成后在 PR 清单里勾选，并在功能清单里更新状态、写上 PR；v2 合回 `main` 时改为「已实现」或「已删」。
- v2 从零建表，所以 `v2` 分支上不需要保持 v1 能跑：旧 Web、旧路由、旧表随对应切片直接删除。移动端、扩展、桌面在 M4 之前不参与 `v2` 分支的类型检查。
- v2.0 发布时 `v2` 合回 `main`。预览环境用空库重建；需要历史数据的部署等迁移工具（M5）。
- v2 预览实例：M0.8 完成后，用空库部署一个 v2 预览实例给 Jim 日常使用（独立域名，不碰 v1 的部署）。真实使用中的失败进 Eval 内环（M2.4）。部署前需要 Jim 确认。
- 每个切片的门槛：`pnpm typecheck`、`pnpm lint`、`pnpm test` 全绿；新 Web 的切片另有 Playwright 用例；跨进程的改动有 db-commit 测试；文档同步（README、AGENTS.md、本目录、设计系统）。

## 并行推进

同时最多开 4 条线，通常 3 条；线多于 4 条时错开开始。

| 线 | 顺序 | 说明 |
| --- | --- | --- |
| 引擎 | M0.8 → M1.7 → M2.4 → M3.6 | 都改 `apps/api/src/engine`。由一个 Agent 串行做，避免同一批文件互相冲突 |
| 知识库网页 | M2.1 网页 → M1.7 的界面（分档卡片、预先授权、定时开关、运行详情里的「结果未知」） | 只动 `apps/web` |
| 表格 | M2.2 人用部分（从 #64 移植）→ M1.7 之后接 Agent 工具与自动化 → M2.3 应用 | 关键路径。人用部分不依赖审批分级，可以马上开始 |
| 邮箱 | M1.8：邮箱服务（系统发信）→ Agent 邮箱（收发；来信叫醒等 M1.7 的唤醒层）→ 个人邮箱的内置连接器 → M3.1 语音 | 和其他线基本不碰同一批文件 |
| 移动端 | M4.1 iOS 与 M4.2 Android 改用 API v2：对话、Agents、运行、通知与推送、电脑 → 知识库 → 表格与应用（随 M2）；逐屏打磨 | 只动 `apps/mobile`；服务端接口变了就跟着改 |
| 整合 | 合并各条线、复审、全量测试、PR 清单与文档 | 由主会话负责。基线迁移、接口入口、路由与文案上的冲突，在合并时处理 |

不能并行的：
- 应用要等表格。
- 移动端的知识库、表格与应用要等对应的接口稳定；对话、Agents、运行、通知、电脑的接口已经稳定，可以先做。
- 迁移（M5）要等表结构定稿。

每条线用独立的测试库和浏览器测试端口。

M1.7 的验收：
- 一个定时运行：读知识库 → 在私有文件夹写草稿（直接执行）→ 提议修改一份共享文档（发卡片，运行进入等待）→ 批准后完成并汇报。
- 三档各一条 db 测试。
- 读过外部内容后，不使用预先授权。
- 在浏览器里点击提交按钮会发卡片。
- 事件超过链深度或每日上限时不叫醒 Agent。

M1.8 的验收：
- 配置邮箱服务后，邀请和重置密码自动发邮件；没配置时仍可复制链接。
- 发到 Agent 邮箱的信进它的对话：名单里的发件人叫醒 Agent，其他留存；入站请求验签，失败拒收。
- Agent 回信先发卡片，批准后从它的地址发出，收件人看到的是同一个邮件线程。
- 成员连上个人邮箱后，Agent 能搜信、读信，发信要批准。
